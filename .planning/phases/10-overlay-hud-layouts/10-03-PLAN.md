  1. **BMP byte-length validation:** Add a console.log in `showOverlayHud()` (glassAdapter.ts ~line 426) that logs the byte length of each BMP BEFORE sending:
     ```
     console.log(`[showOverlayHud] teamBarBmp=${teamBarBmp.length}B, oppBmp=${oppCompositeBmp.length}B, playerBmp=${playerCompositeBmp.length}B`);
     ```
     Expected sizes for 1-bit BMP (BMP header + pixel data):
     - Team bar (576x24): header + ceil(576/8)*24 = 62 + 1728 = 1790 bytes (approximately — verify with encodeBmp math)
     - Composite (144x132): header + ceil(144/8)*132 = 62 + 2376 = 2438 bytes (approximately)
     If playerBmp length equals teamBarBmp length, the cache is swapping them.

  2. **Check encodeBmp BMP header dimensions:** In `SpriteBmpEncoder.ts`, verify that `encodeBmp(pixels, width, height)` writes the width and height into the correct BMP header offsets. BMP format stores width at offset 18 (4 bytes LE) and height at offset 22 (4 bytes LE). If the BMP header has wrong dimensions, the SDK may render the pixel data using incorrect stride, causing "tiny scattered sprites" appearance.

  3. **Check buildSpriteComposite canvas dimensions vs binarize dimensions:** In `CompositeBuilder.ts` line 165, `getCompositeCtx(COMPOSITE_W, COMPOSITE_H)` creates the canvas. Line 214, `binarizeCanvas(ctx, COMPOSITE_W, COMPOSITE_H)` reads pixels. Line 215, `encodeBmp(pixels, COMPOSITE_W, COMPOSITE_H)` encodes. Verify COMPOSITE_W=144 and COMPOSITE_H=132 are used consistently (not accidentally swapped or using team bar dimensions).

  4. **Check SDK imageObject array-index routing:** The Even G2 SDK's `updateImageRawData` uses `containerID` and `containerName` to target the correct container. However, some SDK versions route by the *order* of image containers in the `imageObject` array passed to `rebuildPageContainer`. If the SDK uses array index 0/1/2 instead of containerID 8/4/5:
     - Index 0 = teamBar (gets teamBarBmp) — correct
     - Index 1 = oppSprite (gets oppCompositeBmp) — correct
     - Index 2 = playerSprite (gets playerCompositeBmp) — correct
     This ordering already matches. But if there's an off-by-one or the SDK caches container order from a previous `rebuildPageContainer` call that had DIFFERENT image containers (e.g., `showBattleHud` uses oppSprite at index 0, playerSprite at index 1), the cached order would be wrong.

     **Likely fix if this is the cause:** Ensure `showOverlayHud` sends BMP data in the SAME order as the imageObject array, AND ensure the containerIDs in sendBmpData match. Currently this is already the case. But if `showBattleHud` was called before `showOverlayHud`, the SDK may have cached container mappings from that call. Test by adding a small delay between `renderContainers` and the first `sendBmpData` call (~50ms) to ensure the rebuild completes before image updates.

  5. **Check for stale reference in cache assignment:** In `buildAndCacheComposites()` (ScreenController.ts line 695-703), `Promise.all` returns `[opp, player, bar]` in that order. Verify the destructuring matches: `const [opp, player, bar] = await Promise.all([buildOppComposite, buildPlayerComposite, buildTeamBar])`. If the destructuring order doesn't match the Promise.all order, opp/player/bar would be swapped. This is currently correct per the code.

  **Apply fix based on diagnosis.** Most likely fix paths:
  - If BMP header dimensions are wrong: fix `encodeBmp` to write correct width/height
  - If SDK routes by array index from prior call: add a short delay after `renderContainers` before `sendBmpData`, OR reorder to send in exact array order with explicit comments
  - If cache assignments are swapped: fix destructuring order
  - If the BMP data itself is correct but SDK has a container-mapping quirk: try sending all 3 BMPs via a NEW `rebuildPageContainer` call that includes image data inline rather than separate `updateImageRawData` calls

  **Important:** Do NOT change container IDs, positions, or dimensions unless the diagnosis specifically identifies them as wrong. The 4-container layout geometry is verified correct.
