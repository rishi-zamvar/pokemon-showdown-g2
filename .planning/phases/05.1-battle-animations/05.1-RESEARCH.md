# Phase 5.1: Battle Animations - Research

**Researched:** 2026-02-27
**Domain:** G2 SDK in-place container updates, async animation sequencing, sprite manipulation
**Confidence:** HIGH

---

## Summary

Phase 5.1 transforms the static TURN_RESULT screen into a Game Boy-style animated sequence. Instead of showing all turn events as a text block, the system plays them one-by-one with typewriter text reveal, sprite flash effects on damage, and progressive HP drain -- all concurrent within each event.

The core insight is that the G2 SDK already provides the two primitives needed for animation: `textContainerUpgrade()` for in-place text updates (no rebuild, no flash) and `updateImageRawData()` for in-place sprite updates. Both operate on containers created by `showBattleHud()`. The animation system is purely a sequencer that calls these existing SDK methods on a timer.

The architecture is an `AnimationEngine` class that takes the battle HUD layout (already on screen from `showBattleHud()`) and drives it through a sequence of timed updates. The ScreenController's `resolveTurn()` method transitions to an `ANIMATING` screen state, delegates to the AnimationEngine, and blocks all gestures except tap-to-skip. No new SDK calls, no new npm packages -- just async/await with setTimeout-based timing.

**Primary recommendation:** Build an `AnimationEngine` class in `src/animation/AnimationEngine.ts` that receives the turn log and current battle state, then drives the existing glass adapter's in-place update methods (`textContainerUpgrade` for text, `updateImageRawData` for sprites) on a frame-by-frame timer. Add `updateImage()` to the `GlassAdapter` interface. Add an `ANIMATING` screen state to block gestures.

### Pattern 1: Animation as Async Sequence with Cancellation

**What:** The AnimationEngine runs an async function that iterates through turn log entries, calling glass update methods with `await delay()` between frames. A cancellation token (AbortController or simple boolean flag) allows tap-to-skip to short-circuit the sequence.

**When to use:** Always -- this is the core animation pattern.

**Example:**

```typescript
// src/animation/AnimationEngine.ts
export class AnimationEngine {
  private cancelled = false;
  private running = false;

  /** Skip to end immediately. Idempotent. */
  skip(): void {
    this.cancelled = true;
  }

  isRunning(): boolean {
    return this.running;
  }

  async playTurn(
    log: TurnLogEntry[],
    state: BattleState,
    glass: GlassAdapter,
  ): Promise<void> {
    this.cancelled = false;
    this.running = true;

    try {
      for (const entry of log) {
        if (this.cancelled) break;
        await this.playEntry(entry, state, glass);
        if (this.cancelled) break;
        await this.delay(ANIM.ENTRY_PAUSE_MS); // ~500ms between entries
      }
    } finally {
      this.running = false;
    }
  }

  private async playEntry(
    entry: TurnLogEntry,
    state: BattleState,
    glass: GlassAdapter,
  ): Promise<void> {
    // Launch concurrent operations for this entry:
    // 1. Typewriter text reveal
    // 2. Sprite flash (if DAMAGE/FAINT/MISS)
    // 3. HP drain (if DAMAGE)
    const tasks: Promise<void>[] = [];

    tasks.push(this.typewriterText(formatEntry(entry), glass));

    if (entry.kind === 'DAMAGE') {
      const targetSide = entry.actor === 'player' ? 'opponent' : 'player';
      tasks.push(this.spriteFlash(targetSide, 'hit', glass));
      tasks.push(this.hpDrain(targetSide, entry, state, glass));
    }
    // ... more entry kinds

    await Promise.all(tasks);
  }

  private delay(ms: number): Promise<void> {
    return new Promise(r => {
      if (this.cancelled) { r(); return; }
      setTimeout(r, ms);
    });
  }
}
```

### Pattern 2: In-Place Text Update for Typewriter Effect

**What:** After `showBattleHud()` creates the layout, use `textContainerUpgrade()` on container ID 1 to progressively reveal text character by character. The text container already exists -- we just replace its content.

**When to use:** For typewriter text streaming during animation.

**Critical detail:** The current `showBattleHud()` puts combined opp+player text in container ID 1. During animation, we repurpose this container for narration text. After animation ends, we restore it to the normal battle HUD text.

**Example:**

```typescript
// Typewriter: progressively reveal text in the existing text container
async typewriterText(fullText: string, glass: GlassAdapter): Promise<void> {
  for (let i = 1; i <= fullText.length; i++) {
    if (this.cancelled) break;

    const partial = fullText.slice(0, i);
    await glass.updateText(partial, { left: 'Battle', right: '' });

    const char = fullText[i - 1];
    const isPunctuation = '.!?'.includes(char);
    const delayMs = isPunctuation ? ANIM.PUNCTUATION_PAUSE_MS : ANIM.CHAR_DELAY_MS;
    await this.delay(delayMs);
  }
}
```

### Pattern 3: Sprite Flash via In-Place Image Update

**What:** Use `updateImageRawData()` on existing sprite containers (ID 4 for opponent, ID 5 for player) to swap between normal, inverted, and blank sprites.

**When to use:** For damage hit, miss, and faint effects.

**Example:**

```typescript
// Flash sequence: invert -> restore -> blank -> restore (x2 for hit)
async spriteFlash(
  side: 'player' | 'opponent',
  effect: 'hit' | 'miss' | 'faint',
  glass: GlassAdapter,
): Promise<void> {
  const normal = getSpriteBase64(side);
  const inverted = invertSprite(normal); // Canvas API
  const blank = ''; // empty string = blank container

  const cycles = effect === 'faint' ? 3 : 2;
  for (let i = 0; i < cycles; i++) {
    if (this.cancelled) break;
    await glass.updateImage(side, inverted);
    await this.delay(ANIM.FLASH_FRAME_MS);    // ~75ms
    await glass.updateImage(side, normal);
    await this.delay(ANIM.FLASH_FRAME_MS);
    await glass.updateImage(side, blank);
    await this.delay(ANIM.FLASH_FRAME_MS);
    await glass.updateImage(side, normal);
    await this.delay(ANIM.FLASH_FRAME_MS);
  }

  if (effect === 'faint') {
    await glass.updateImage(side, blank); // permanently remove
  }
}
```

### Pattern 4: HP Drain via Repeated Text Updates

**What:** Calculate intermediate HP values between old and new, then rapidly call `updateText()` to show the bar draining. Reuse `formatHpBar()` from battleHudRenderer.

**When to use:** For DAMAGE entries.

**Example:**

```typescript
async hpDrain(
  side: 'player' | 'opponent',
  entry: TurnLogEntry,
  state: BattleState,
  glass: GlassAdapter,
): Promise<void> {
  const damage = entry.detail.damage as number;
  const mon = getActiveMon(state, side);
  const startHp = mon.currentHp + damage; // HP before this hit
  const endHp = mon.currentHp;
  const steps = Math.min(Math.abs(damage), ANIM.MAX_HP_STEPS);

  for (let i = 0; i <= steps; i++) {
    if (this.cancelled) break;
    const currentHp = Math.round(startHp - (damage * i / steps));
    const hpText = formatHpBar({ ...mon, currentHp });
    // Update text container with new HP display
    await glass.updateText(buildNarrationWithHp(hpText, side), statusBar);
    await this.delay(ANIM.HP_FRAME_MS); // ~30-50ms per step
  }
}
```

### Anti-Patterns to Avoid

- **Calling `rebuildPageContainer()` during animation:** This causes a full display flash. Always use `textContainerUpgrade()` and `updateImageRawData()` for in-place updates.
- **Firing concurrent BLE operations:** The G2 BLE link serializes commands. Sending multiple `textContainerUpgrade` + `updateImageRawData` simultaneously may cause dropped frames. Use `await` for each SDK call, but run *logical* operations (text + sprite + HP) concurrently using `Promise.all` where each branch `await`s its own calls sequentially.
- **Updating too fast:** BLE has latency. If you send text updates every 40ms for typewriter but BLE takes 50ms per round-trip, updates will queue up and display out of order. The 40ms target is a minimum *display interval*, not a *send interval*. Each `await glass.updateText()` will naturally pace itself.
- **Blocking the main thread:** All animation must be async. Never use synchronous loops or `while(true)` patterns.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PNG pixel inversion | Custom binary PNG parser | Canvas API `getImageData()` + pixel loop + `toDataURL()` | Canvas handles PNG decode/encode, color space, alpha; binary PNG parsing is 200+ lines |
| Async delay with cancellation | Custom promise chain | Simple `delay()` with cancelled flag check | Works with async/await; AbortController is overkill for single-consumer |
| Text formatting | New formatter for animation | Existing `formatEntry()` from turnResultRenderer | Already handles all 12 entry kinds; just import and reuse |
| HP bar rendering | New HP bar for animation | Existing `formatHpBar()` from battleHudRenderer | Already handles percentage, filled/empty blocks |

**Key insight:** The animation system is a sequencer, not a renderer. All rendering primitives (text formatting, HP bars, sprite data) already exist. The new code only needs to orchestrate *when* to call them.

## Common Pitfalls

### Pitfall 1: BLE Throughput Bottleneck

**What goes wrong:** Sending updates too frequently causes BLE command queue backup. The display stutters or shows stale frames.
**Why it happens:** BLE has ~15-30ms minimum round-trip per command. Typewriter at 40ms/char + HP drain at 30ms/step + sprite flash at 75ms/frame can exceed BLE bandwidth if all fire simultaneously.
**How to avoid:** Each concurrent branch (text, sprite, HP) must `await` its own SDK calls. `Promise.all` only parallelizes the *logic*, not the BLE calls. Monitor actual frame rate on hardware and increase delays if needed.
**Warning signs:** Text appearing out of order, sprite flashes showing wrong image, HP jumping instead of draining.

### Pitfall 2: Race Between Animation and Gesture Handler

**What goes wrong:** User taps during animation, triggering both `skip()` and a regular navigation gesture. After skip completes, the stale gesture navigates to the wrong screen.
**Why it happens:** `handleGesture()` is called asynchronously by the SDK event system. If gesture blocking is not checked before every handler, stale events leak through.
**How to avoid:** Check `animationEngine.isRunning()` at the TOP of `handleGesture()` in ScreenController. If running and gesture is TAP, call `skip()`. If running and gesture is anything else, return immediately (swallow it).
**Warning signs:** Screen flickering after animation, navigating to ACTION_MENU during animation.

### Pitfall 3: Container ID Mismatch After Layout Change

**What goes wrong:** `textContainerUpgrade()` fails silently because the container ID doesn't match what was created by `showBattleHud()`.
**Why it happens:** If any code path calls `showList()` or `showText()` (which rebuild with different container IDs) between `showBattleHud()` and the animation updates, the containers no longer exist.
**How to avoid:** Ensure NO rebuilds happen during animation. The animation always starts from a `showBattleHud()` layout and only uses in-place updates until animation completes. After animation, transition to the next screen (which may rebuild).
**Warning signs:** `textContainerUpgrade` returning false, display going blank during animation.

### Pitfall 4: Stale State After Skip

**What goes wrong:** After tap-to-skip, the display shows intermediate state instead of the final state.
**Why it happens:** `cancelled = true` stops the loop, but the last frame that was being sent might be an intermediate HP value or partial text.
**How to avoid:** After the animation `playTurn()` resolves (whether cancelled or completed), always write the FINAL state to the display: full text of last entry, final HP values, final sprite states (including removing fainted sprites). This is the "skip cleanup" step.
**Warning signs:** HP bar showing wrong value after skip, partial text visible after skip.

### Pitfall 5: Inverted Sprite Cache Bloat

**What goes wrong:** Creating inverted sprites on every flash frame adds ~5KB base64 strings per sprite per frame to memory.
**Why it happens:** Canvas `toDataURL()` creates a new string each time.
**How to avoid:** Pre-compute the inverted sprite once when animation starts for that entry. Cache it for the duration of the flash sequence, then discard. Do NOT persist to localStorage.
**Warning signs:** Memory usage climbing during long battles, GC pauses causing animation stutter.

### Pitfall 6: Text Container Content Overlap

**What goes wrong:** During animation, the narration text overlaps with the opp/player stat text because both use container ID 1.
**Why it happens:** `showBattleHud()` puts combined opp+player info in the text container. During animation, we replace this with narration text. But the sprites expect their adjacent text.
**How to avoid:** During animation, the text container (ID 1) is repurposed for narration-only text (centered below sprites). After animation, restore it to the normal HUD text. The sprites (containers 4 and 5) remain in place throughout since they're separate image containers.
**Warning signs:** Garbled text during animation, stat text appearing in narration area.

## Code Examples

### Example 1: Inverting a Base64 PNG Sprite via Canvas

```typescript
// src/animation/SpriteEffects.ts
/**
 * Invert a base64 PNG to create a "flash" effect.
 * Input: raw base64 string (no data: prefix).
 * Output: raw base64 string with pixels inverted.
 */
export function invertSprite(base64: string): Promise<string> {
  return new Promise((resolve, reject) => {
    const img = new Image();
    img.onload = () => {
      const canvas = document.createElement('canvas');
      canvas.width = img.width;
      canvas.height = img.height;
      const ctx = canvas.getContext('2d')!;
      ctx.drawImage(img, 0, 0);

      const imageData = ctx.getImageData(0, 0, canvas.width, canvas.height);
      const data = imageData.data;

      // Invert RGB, preserve alpha
      for (let i = 0; i < data.length; i += 4) {
        data[i] = 255 - data[i];       // R
        data[i + 1] = 255 - data[i + 1]; // G
        data[i + 2] = 255 - data[i + 2]; // B
        // data[i + 3] unchanged (alpha)
      }

      ctx.putImageData(imageData, 0, 0);
      const result = canvas.toDataURL('image/png');
      // Strip "data:image/png;base64," prefix
      const commaIdx = result.indexOf(',');
      resolve(commaIdx >= 0 ? result.slice(commaIdx + 1) : result);
    };
    img.onerror = reject;
    img.src = `data:image/png;base64,${base64}`;
  });
}

/** Create a 1x1 transparent PNG as "blank" sprite. */
export function blankSprite(): string {
  const canvas = document.createElement('canvas');
  canvas.width = 1;
  canvas.height = 1;
  const result = canvas.toDataURL('image/png');
  const commaIdx = result.indexOf(',');
  return commaIdx >= 0 ? result.slice(commaIdx + 1) : result;
}
```

## Open Questions

1. **Minimum BLE update interval on real hardware**
   - What we know: The SDK calls are async and return a Promise. The adapter already uses sequential `await` for image updates. `textContainerUpgrade` returns a boolean.
   - What's unclear: The actual minimum interval between successive `textContainerUpgrade()` calls before the display drops frames. 40ms target may be too aggressive on BLE.
   - Recommendation: Start with 45ms character delay. If BLE is slower, the `await` will naturally pace it. Add a `MIN_UPDATE_INTERVAL` constant that can be tuned. Log actual frame timing in dev mode.

2. **Blank sprite behavior**
   - What we know: `updateImageRawData()` sends image data to an existing container.
   - What's unclear: What happens if you send an empty string or a 1x1 transparent PNG -- does it clear the container visually, or does it show a broken image indicator?
   - Recommendation: Use a 1x1 transparent PNG for "blank" (not empty string). Test on hardware. If it doesn't clear visually, use a solid black 64x64 PNG that matches the background.

3. **Concurrent BLE command ordering**
   - What we know: The existing code sends image updates sequentially. `Promise.all` on multiple `textContainerUpgrade` + `updateImageRawData` calls would send them in arbitrary order over BLE.
   - What's unclear: Whether the G2 firmware can handle interleaved text + image updates, or whether text updates must all complete before image updates (or vice versa).
   - Recommendation: Within each animation "frame", send text update first, then image update, all sequential. Concurrency is at the *logical operation* level (text typewriter vs. sprite flash vs. HP drain run as parallel async functions), but each function's BLE calls are sequential within themselves. If BLE commands from different parallel branches interleave, that should be fine since they target different container IDs.
