## Why one line goes into src/

The phase boundary says this phase observes and changes no gameplay or rendering
behaviour. One `console.log` is added to `ScreenController.render()` — the single
render funnel at line 725 — emitting:

```
[screen] BATTLE_HUD cursor=0
```

It goes **after the `switch` closes** (~line 790, immediately before
`if (this.state.battleState)`), not at the top. The switch is where the actual glass
work happens: every decision screen awaits `showOverlayHud`, which sends 3 images at
~104 ms each plus a ~165 ms rebuild (research §3). A line logged at the top of
`render()` fires ~477 ms before those pixels exist, so `waitScreen` would return while
the OUTGOING screen is still on the framebuffer and every `expectFrameInk` would
assert against the previous screen. Placed after the switch, the line means what
`waitScreen` needs it to mean: the render is complete.

Without it the harness has no screen oracle. Ink coverage cannot distinguish
BATTLE_HUD from ATTACK_SELECT, so a scripted battle could not tell whether an input
landed, could not detect END_SCREEN to stop looping, and D-15 ("wait on conditions")
would degrade into fixed sleeps and guessed turn counts. This is instrumentation,
not behaviour: no branch, no render change, no timing change. It is also the hook
that Phases 14/16/17 hang `expectLoggedLine` on.

## The negative proof is the deliverable that makes the rest trustworthy

## No fixed settle after waitScreen — and why that is safe

D-15 allows a fixed delay "where the platform's own fixed costs require it". With the
log line placed after the switch (above), that clause is consciously **not invoked**:
`render()` awaits every glass call before logging, so the line is emitted only once the
SDK calls have resolved and the framebuffer is current. `capture()` therefore needs no
settle. The one platform delay that remains is internal to the adapter — the
deliberate 50 ms wait after `rebuildPageContainer` before image sends
(glassAdapter.ts ~:438) — and it sits inside the awaited call, so it is already covered.
If a future frame turns out to lag its log line, add a polled condition
(`waitFor(ink > 0)`), never a `setTimeout`.

## The negative proof is the deliverable that makes the rest trustworthy

A harness whose assertions always pass is worse than no harness. `negativeProof.ts`
deliberately asserts ink in a region that is known to be blank, catches the throw,
and **fails the run if no throw occurred**. It also refuses to "prove" HARN-02 unless
the stdout tee is demonstrably alive — see Task 3.
