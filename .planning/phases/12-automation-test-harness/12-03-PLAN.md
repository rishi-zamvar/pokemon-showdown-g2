<objective>
Wire the primitives into a runnable suite: the assertion vocabulary, the runner
behind `npm run harness`, a boot scenario, and a negative scenario that proves the
assertions actually detect defects.

Purpose: HARN-06 (one command, headless), HARN-03 (framebuffer content assertions
that fail on blank), HARN-05 (any error/uncaught/failed fetch/validation warning
fails the run). This plan also fixes the assertion names the ROADMAP commits to for
Phases 13-19 — every later phase cites `expectFrameInk`, `expectConsoleClean`,
`expectLoggedLine`, `expectHostCalls` by name, so the signatures here are a contract.

Output: `harness/assert.ts`, `harness/run.ts`, three scenarios, `npm run harness`,
and exactly one line added to `src/`.

## Why one line goes into src/

The phase boundary says this phase observes and changes no gameplay or rendering
behaviour. One `console.log` is added to `ScreenController.render()` — the single
render funnel at line 725 — emitting:

```
[screen] BATTLE_HUD cursor=0
```

Without it the harness has no screen oracle. Ink coverage cannot distinguish
BATTLE_HUD from ATTACK_SELECT, so a scripted battle could not tell whether an input
landed, could not detect END_SCREEN to stop looping, and D-15 ("wait on conditions")
would degrade into fixed sleeps and guessed turn counts. This is instrumentation,
not behaviour: no branch, no render change, no timing change. It is also the hook
that Phases 14/16/17 hang `expectLoggedLine` on.

## The negative proof is the deliverable that makes the rest trustworthy

A harness whose assertions always pass is worse than no harness. `negativeProof.ts`
deliberately asserts ink in a region that is known to be blank, catches the throw,
and **fails the run if no throw occurred**. It is scenario zero of every run.

</objective>

export interface Ctx {

    **harness/assert.ts** — implement the vocabulary above. All assertions throw
    `AssertionError` with a message naming the region/pattern AND the observed value,
    because the message is what a failing run prints.
    - `expectFrameInk(f, r, min, max)`: `const got = inkRatio(f, r)`; throw unless
      `min <= got <= max`. Message: `` `${r.name}: ink ${got.toFixed(3)} outside [${min}, ${max}]` ``.
      This is the blank/saturated detector — HARN-03 and D-06. It is the assertion
      that would have caught a screen that renders nothing while logging no error.
    - `expectGreyLevels(f, r, n)`: throw unless `greyLevels(f, r) >= n`. Phase 15 uses it.
    - `expectRegionPersists(frames, r, min = 0.01)`: throw naming the FIRST frame index
      whose ink drops below `min`. Phase 14 uses it across animation frames.
    - `expectConsoleClean(logs)`: `const bad = logs.failures()`; throw listing every
      failing line with its `source` prefix. This is HARN-05 and it is the assertion
      that must fail on the stdout-only container-validation line.
    - `expectLoggedLine(logs, pattern)`: return the first `logs.all()` line matching,
      else throw listing the last 10 lines seen so a mismatch is debuggable.
    - `expectHostCalls(logs, method, max)`: throw unless
      `(logs.hostCalls()[method] ?? 0) <= max`. Phase 19 / PERF-04 uses it; D-13 only
      requires that the number be recorded now.
    - `expectScreen(logs, name)`: `expectLoggedLine(logs, new RegExp(`\\[screen\\] ${name}\\b`))`.

    Add a header comment listing the ROADMAP Phase 12 assertion table and which later
    phase consumes each entry, so nobody renames these casually.
    `expectFrameDiff` and `runBattleScript` from that table are deliberately NOT here:
    golden-image diffing is ruled out by D-10, and `runBattleScript` is plan 12-04.

         the scenario boundary.
