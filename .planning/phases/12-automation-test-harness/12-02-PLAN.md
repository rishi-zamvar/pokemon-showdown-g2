## The stdout requirement is the point of this phase

A harness that reads only `/api/console` would have passed the defect that made the
game unplayable. The simulator writes container validation failures to its own stdout:

```
[2026-09-17T16:36:58Z WARN evenhub_simulator_lib::flutter] RebuildPageContainer validation failed: image container size 576x24 exceeds maximum 288x144
```

That line appears nowhere in `/api/console`. Capturing it is HARN-02 and D-03, and
is the single highest-value line of code in Phase 12.

## Verified launch facts — do not rediscover these

- `even-dev/start-even.sh` calls `npx --yes @evenrealities/evenhub-simulator@latest`,
  which FAILS with "command not found" — the package's bin is not linked. Spawn the
  platform binary directly:
  `./node_modules/@evenrealities/sim-darwin-arm64/bin/evenhub-simulator http://127.0.0.1:5173 --automation-port 9898`
- The app is served by the sibling harness, not this repo's `npm run dev` (even-dev
  supplies the Vite plugins and the `public/` asset symlinks whose breakage was
  defect #1 in the research doc):
  `cd ../even-dev && ./start-even.sh pokemon-showdown --web-only`
- `start-even.sh --web-only` blocks on `wait $VITE_PID` and spawns `npx vite` as a
  child, so it must be spawned `detached: true` and killed as a process **group**
  (`process.kill(-pid)`), or Vite survives teardown and holds port 5173.
- Node 22.20 runs `.ts` files natively (type stripping). Relative imports must carry
  the `.ts` extension. `harness/tsconfig.json` and the `typecheck:harness` script are
  created by plan **12-01**, which is why this plan is wave 2 and depends on it — this
  plan also appends to `harness/selfCheck.ts` and its verifies run `npm run typecheck:harness`.
  Copy the Node-version guard from `harness/selfCheck.ts` verbatim into `harness/probe.ts`.

## The attach path is where HARN-02 quietly dies

D-12 allows attaching to an already-running simulator. But when we attach there is no
child process to tee, so `onStdout` is never called, `LogStream` sees console entries
only, `expectConsoleClean` keeps passing, and the run goes green with stdout capture
completely dead. That is the single most important requirement in the phase silently
switching itself off. Two mechanisms close it, both in this plan:
- `LogStream.stdoutLineCount` is **monotonic** — `reset()` clears `lines` but must NOT
  zero this counter. A run can therefore ask "did the tee ever produce anything?"
  even after per-step console resets.
- `SimHandle.stdoutAvailable` is `false` on the attach path, and attaching requires an
  explicit `--attach` flag. Without the flag, `startStack` refuses to attach and fails
  naming HARN-02.

export type InputAction =
  | "up" | "down" | "click" | "double_click"
  | "long_press" | "long_press_release" | "context_menu";

export interface ConsoleEntry {
  id: number;
  level: string;      // "log" | "warn" | "error" | "info" | "debug"
  message: string;
  ts: string;
}

export class Driver {
  constructor(port: number);
  readonly port: number;
  ping(): Promise<boolean>;                  // false instead of throwing when unreachable
  glasses(): Promise<Uint8Array>;            // GET /api/screenshot/glasses (576x288 RGBA PNG bytes)
  webview(): Promise<Uint8Array>;            // GET /api/screenshot/webview
  consoleSince(id: number): Promise<{ entries: ConsoleEntry[]; total: number }>;
  clearConsole(): Promise<void>;             // DELETE /api/console
  input(action: InputAction): Promise<void>; // POST /api/input {"action": ...}
}

export interface WaitOpts { what: string; timeoutMs?: number; pollMs?: number }
/** Polls fn() until it returns a non-null value. Throws naming `what` on timeout. */
export function waitFor<T>(fn: () => Promise<T | null>, opts: WaitOpts): Promise<T>;
```

export interface LogLine {
  seq: number;                     // harness-assigned ordering across both sources
  source: "console" | "stdout";
  level: string;                   // console level, or parsed stdout level
  message: string;
}
export function isFailureLine(l: LogLine): boolean;

export class LogStream {
  constructor(driver: Driver);
  pushStdout(rawLine: string): void;
  /** DELETE /api/console, drop local buffer, reset since_id. Call per scenario step. */
  reset(): Promise<void>;
  /** Drain new console entries; returns everything new since the last poll. */
  poll(): Promise<LogLine[]>;
  all(): LogLine[];
  failures(): LogLine[];
  /** Host-call counts observed since the last reset, keyed by SDK method name. */
  hostCalls(): Record<string, number>;
  /** Next seq value that will be assigned. Watermark for "only lines after this point". */
  nextSeq(): number;
  /** Monotonic count of stdout lines EVER teed. reset() must not zero this. */
  readonly stdoutLineCount: number;
}
```

  <action>
    Implement `Driver` over Node 22's global `fetch` — no HTTP library (HARN-01).
    Base URL `http://127.0.0.1:${port}`.

    - `ping()`: GET `/api/ping` with `AbortSignal.timeout(1500)`; return
      `res.ok &amp;&amp; (await res.text()).trim() === "pong"`; return `false` on any
      throw. Never rejects — callers poll it.
    - `glasses()` / `webview()`: GET the screenshot endpoints; throw on non-2xx with
      status and endpoint in the message; return `new Uint8Array(await res.arrayBuffer())`.
      These return raw PNG bytes, not base64 or JSON.
    - `consoleSince(id)`: GET `/api/console?since_id=${id}`, parse JSON
      `{ entries, total }`. D-04 requires incremental polling — never re-read the
      whole buffer.
    - `clearConsole()`: DELETE `/api/console`.
    - `input(action)`: POST `/api/input` with `content-type: application/json` and
      body `JSON.stringify({ action })`. Throw unless the response parses to
      `{ ok: true }`. Add a comment recording the constraint from the simulator
      README: input is silently ignored when no container has `isEventCapture: 1`,
      so a dropped input is indistinguishable from a no-op at this layer and callers
      must assert the screen actually changed (plan 12-03's job).

    `waitFor(fn, { what, timeoutMs = 15_000, pollMs = 250 })`: loop calling `fn()`,
    return the first non-null result, and on timeout throw
    `timed out after {timeoutMs}ms waiting for: {what}`. Swallow exceptions thrown by
    `fn` while polling (a screenshot taken mid-rebuild can legitimately fail) but
    append the last one to the timeout message. This is the ONLY waiting primitive in
    the harness — D-15 forbids fixed sleeps.
