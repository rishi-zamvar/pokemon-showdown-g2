## Decisions Made

- **Check 53 was added rather than left to plan 03/04.** `MAIN_MENU_CONTEXT_MENU` is the array Phase 17 edits, and "Exit last" has no other enforcement anywhere in the tree. `constants.ts` is importable by the harness (no `.js` specifiers) and the SDK imports cleanly from `harness/` over ESM, so the check runs the *real* validator against the *real* constant wrapped exactly as `renderContainers` wraps it — not a stand-in.
- **`assert.ok(m.id !== 0, …)` was dropped from check 53.** `as const` narrows the ids to the literal union `1 | 2 | 3` and `tsc -p harness/tsconfig.json` rejects the comparison with TS2367. The rule is still enforced twice over — by the SDK on the real menu, and by the `INVALID_MENU_ITEM_ID` refusal case. A comment in the check says so.
- **No entry added to `harness/logs.ts`'s `HOST_CALL_PATTERNS` for `shutDownPageContainer`.** Plan 04 asserts via `expectLoggedLine`, which needs no table entry, and adding a host-call category nothing counts yet is the kind of speculative scaffolding Phase 19 should own. Flagged under Next Phase Readiness in case plan 04 wants `expectHostCalls` instead.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] The plan's task-3 verify gate (fix A5) did not catch what it claimed to catch**

- **Found during:** Task 3, while proving falsifiability.
- **Issue:** The gate asserted `(branch.match(/\breturn;/g)||[]).length < 2` with the stated intent "both the missing-itemID path and the handled path must return". The branch as specified by the plan has **three** exits — missing-itemID, dedupe-drop, and handled — so a threshold of 2 has a spare return. Deleting the handled-path `return;` (break E) or the missing-itemID `return;` (break F) left 2 and **the gate stayed green** while a menu click fell straight through into `mapEventToGesture` and became a stray TAP. That is precisely the regression A5 exists to prevent, and the gate as written permits it. Verified empirically, not reasoned about: both breaks printed `ok`.
- **Fix:** Raised the threshold to `< 3` with an error message naming all three paths, and a comment in the gate explaining why 2 is not enough. Re-ran breaks E, F and G — all three now red; correct code green.
- **Files modified:** none in `src/` (the gate is plan text, executed at verify time; the corrected gate is recorded here and in the task 3 commit message).
- **Verification:** the falsifiability table above, rows E/F/G.
- **Committed in:** `7e94838`

Hand-offs and cautions:

- **Plan 04's boot assertion** should match the exact string `[GlassAdapter] menu declared: 3 item(s)`, logged from `renderContainers` *after* `assertPage` returns. It fires once per root-page render, so a boot that renders the root page twice logs it twice.
- **Plan 04's exit assertion** should match `[GlassAdapter] shutDownPageContainer(1)` — the **pre**-call line. The `-> ${ok}` line may never arrive if the dialogue wedges the bridge.
- **`expectHostCalls` cannot count the exit call.** `harness/logs.ts`'s `HOST_CALL_PATTERNS` has no `shutDownPageContainer` entry; if plan 04 wants a count rather than a line, it must add one (one row, next to the existing `rebuildPageContainer` known-zero placeholder).

- **The dedupe has no runtime test, only a source-text gate.** `bindEvents` is a private closure in a module Node cannot import (`src/` uses extensionless/`.js` specifiers), so the 600 ms window is proved structurally here and behaviourally by plan 03's `context_menu` scenario. That is the one real gap in this plan's proof and plan 03 owns it.
- **Do not select Exit in any harness scenario before plan 04's terminal step.** One selection wedges every subsequent `updateImageRawData` for the rest of the process (D-02).
