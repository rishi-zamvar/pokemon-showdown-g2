# Phase 13.1 Plan 02: Wire the Context Menu and Delete the Soft-Brick — Summary

**The root page now declares a live context menu the firmware really renders — proved in the simulator log, Exit last — and the main-menu state that made "Enter Battle" permanently unreachable after one speed change is gone rather than guarded.**

## Performance

- **Duration:** 38 min
- **Tasks:** 2/2
- **Files modified:** 5 (+1 created), 239 insertions, 68 deletions
- **Commits:** 5

## What shipped

### Task 1 — the main menu is one row (`42fae1b`)

`renderMainMenu()` returns `items: ['Enter Battle']` and moves the speed preset
into the status line, which was already being rendered and so costs no extra
host call. Live payload:

```
item_container: ListItemContainerProperty { item_count: Some(1), item_name: Some(["Enter Battle"]) }
content: Some("Pokemon Showdown G2  ·  Speed: Normal")
```

### Task 2 — MENU_ITEM routed, exit gated, soft-brick deleted (`2768525`)

- `render()`'s `MAIN_MENU` case is the only `showList` of three that passes a
  third argument. `END_SCREEN` and `SPRITE_REFRESH` stay two-arg and now carry
  a comment saying the omission is deliberate (D-09).
- `handleGesture` gained `case 'MENU_ITEM'` → `onMenuItem(event.menuItemID)`.
- `onMenuItem` guards on `this.state.screen !== 'MAIN_MENU'`, then routes
  Exit → `glass.exitApp()`, Battle Speed → `SpeedConfig.cycle()` + re-render,
  About → `showText`.
- `handleMainMenu` is one `if` and writes no `cursorIndex` at all. The switch,
  `SpeedConfig.cycle()` inline and the `cursorIndex: 1` write are gone.
- `onDoubleTap` has an explicit, documented `MAIN_MENU` no-op instead of
  falling through `default: break`.

The menu is live, not just declared in source — from the run log:

```
RebuildPageContainer ... menu_object: Some(MenuContainerProperty { menu_items: Some([
  MenuItemProperty { item_name: "Battle Speed", item_id: 2 },
  MenuItemProperty { item_name: "About",        item_id: 3 },
  MenuItemProperty { item_name: "Exit",         item_id: 1 } ]) })
```

Exit is last, as D-02 requires. **Exit was never selected during this plan** —
plan 04 owns that terminal scenario.

The seventh break is worth calling out: it passed on the first attempt. The
gate bounded `onDoubleTap` with `indexOf("// ------")`, which never matches in
a comment-stripped view, so the slice ran to end-of-file and matched
`case 'MAIN_MENU': {` from `render()`. Exactly the spare slot wave 1 warned
about, caught only because the break was actually attempted. Fixed to bound on
the next member declaration.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] The plan's own comments trip the plan's own gates**

- **Found during:** Task 2
- **Issue:** the D-01 comment the plan dictates contains the literal
  `shutDownPageContainer`, and the `handleMainMenu` comment contains the
  literal `cursorIndex: 1`. Both gates are grep-strength by design, so both
  fired: `ScreenController must not call shutDownPageContainer directly` and
  `harness-01 soft-brick state still present`.
- **Fix:** reworded the comments ("must NOT raise the exit dialogue", "left the
  cursor at index 1"). The gates were not loosened — to grep, a comment quoting
  the forbidden string is indistinguishable from the real thing, and the
  briefed rule is that ScreenController must contain no reference at all.
- **Files:** `src/screens/ScreenController.ts`
- **Commit:** `2768525`

**2. [Rule 3 - Blocking] selfCheck 32 counted the `[screen]` prefix, not the oracle**

- **Found during:** Task 2
- **Issue:** the plan's `[screen] menu itemID=...` guard line is a template
  literal with the `[screen] ` prefix, so check 32's
  `/console\.log\(`\[screen\] /g` read 2 emits and the suite went to 52/53.
  Plans 03 and 04 assert on these exact strings, so changing the prefix was
  not an option.
- **Fix:** rewrote the assertion to the real invariant — exactly one ORACLE
  emit (`[screen] ${this.state.screen} cursor=`), plus every other `[screen] `
  line must continue with a lowercase literal so neither `expectScreen`'s
  `/\[screen\] NAME\b/` nor `lastScreen`'s `/\[screen\] ([A-Z_]+)/` can mistake
  it for a screen announcement. Strictly stronger: it now also rejects a second
  emit that interpolates a screen name, which the old regex allowed.
- **Files:** `harness/selfCheck.ts`
- **Commit:** `98f1b7f`

**3. [Rule 1 - Bug] Two framebuffer ink floors were calibrated for a three-row list**

- **Found during:** post-task live verification
- **Issue:** `boot / boot` and `battle / menu` both assert
  `expectFrameInk(frame, REGIONS.CONTENT, 0.01, 0.6)` on the main menu. A
  one-row list inks CONTENT at **0.0046** (measured off
  `.harness-runs/2026-09-22T17-33-15-958Z/boot-001-screen-MAIN_MENU.png`), so
  both failed with `CONTENT: ink 0.005 outside [0.01, 0.6]`.
- **Fix:** floor lowered to 0.002 at both sites, each with a comment naming the
  measured value. `battle.ts` already used exactly this pattern for END_SCREEN
  (0.002, "measured 0.006"); the main menu is now the sparsest screen in the
  app. A blank region still scores 0.000 and still fails — the only property
  the floor ever had.
- **Files:** `harness/scenarios/boot.ts`, `harness/scenarios/battle.ts`
- **Commits:** `fa010ec`, `252e7ae`

**4. [Rule 3 - Blocking] battle.ts's speed path clicked a list row that no longer exists**

- **Found during:** Task 1 impact review
- **Issue:** `runBattleScript({ speed: "Fast" | "Instant" })` did
  `select(1)` + clicks to cycle the preset. On a one-row list that click
  resolves to item 0 and enters a battle, then waits 30 s for a `MAIN_MENU`
  that never comes. Only reached via an explicit non-default option, so the
  suite was not red, but the ROADMAP names `runBattleScript` for Phases 14/17/19.
- **Fix:** throws an `AssertionError` naming the cause and pointing at plan
  03's `context_menu` vocabulary — which is what the `speed` JSDoc already
  claimed it did. Dead `SPEED_CLICKS` deleted. The harness-01 header note was
  marked FIXED rather than deleted: the zero-dropping quirk behind it is still
  live and still the reason `select(0, true)` exists.
- **Files:** `harness/scenarios/battle.ts`
- **Commit:** `fa010ec`
