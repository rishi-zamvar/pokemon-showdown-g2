# Phase 13.1: Store Blocker — Exit Dialogue via Context Menu - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning
**Mode:** --auto

<domain>
## Phase Boundary

Clear the one hard Even Hub submission blocker: the root page must invoke the
exit dialogue on double-tap. Deliver it through a native context menu so the
dialogue cannot be reached by accident. Covers INPUT-05, INPUT-02, INFO-01.

This phase does NOT add inspect screens — Phase 17 extends the menu this phase
creates. It does not change battle rendering.

</domain>

<decisions>
## Implementation Decisions

### Why a menu and not a bare double-tap
- **D-01:** Root double-tap opens the context menu. An explicit "Exit" item
  calls `shutDownPageContainer(1)`. Root double-tap must NOT call it directly.
- **D-02:** This is a safety decision, not a style one. Once the exit dialogue
  has been shown and dismissed, **every `updateImageRawData` returns
  `sendFailed` in 1-3 ms** — an immediate rejection with no transfer — and does
  not recover until the app restarts. Three in-app recoveries were tried
  upstream and all failed: rebuilding on appearance wipes the images, rebuilding
  after cancel does not clear the wedge, and re-calling
  `createStartUpPageContainer` is rejected with `invalid` after blocking ~2.1 s.
  Firing the dialogue from every root double-tap maximises exposure to an
  unrecoverable state. EvenChess uses the menu pattern for exactly this reason.
- **D-03:** No non-root screen calls `shutDownPageContainer` at all.

### What goes in the menu — and a bug this fixes for free
- **D-04:** Menu items at this phase: **Exit**, **Battle Speed**, **About**.
  Inspect entries are Phase 17's job.
- **D-05:** Moving Battle Speed and About off the main-menu *list* and into the
  menu **structurally fixes harness-01**, a live bug that would fail review.
  Today `handleMainMenu` case 1 sets `cursorIndex: 1` when it cycles speed. The
  simulator omits `currentSelectItemIndex` when the selection is 0 (the same
  zero-dropping quirk the app already documents for `CLICK_EVENT`), so
  `mapEventToGesture` hands ScreenController `listIndex: undefined` and `onTap`
  falls back to `cursorIndex`. After ONE speed change every further click on the
  main menu cycles speed again and **"Enter Battle" becomes permanently
  unreachable**. Verified live.
  With speed and about in the menu, the main menu list holds a single item,
  `cursorIndex` never leaves 0, and the fallback is harmless. This is a better
  fix than special-casing the index, because it removes the state that causes it.
- **D-06:** The main menu keeps "Enter Battle" as its only list row.

### Menu mechanics
- **D-07:** Declare via `menuObject` on the root page's
  `createStartUpPageContainer` / `rebuildPageContainer`. Max 10 items; each
  `itemID` non-zero and unique; names within 32 UTF-8 bytes. Validate before
  the SDK call — the SDK rejects invalid menus, and a rejected page builds
  nothing.
- **D-08:** Parse `menuItemClickEvent` through `onEvenHubEvent` alongside the
  existing list/text/sys handling (INPUT-02).
- **D-09:** Rebuilding WITHOUT `menuObject` clears the custom menu and restores
  the default. Non-root pages should omit it deliberately so the menu is a
  root-page affordance, not a global one.

### Proving it
- **D-10:** The harness drives `POST /api/input {"action":"context_menu"}`,
  which the simulator supports. Assert the menu region gains ink and that a
  menu item click is logged.
- **D-11:** `expectConsoleClean()` across `runBattleScript()` must show no
  accidental shutdown mid-battle — the failure mode this phase exists to
  prevent is an unintended exit, so absence of it is the real assertion.

</decisions>

<constraints>
## Known Constraints

- `shutDownPageContainer(0)` closes directly; `(1)` asks the foreground layer to
  decide, which is the dialogue. The submission requirement is the dialogue.
- The firmware emits DUPLICATE sys events ~50-100 ms apart for one physical
  transition. Dedupe by (type, timestamp) over ~600 ms or one double-tap opens
  the menu twice.
- `CLICK_EVENT = 0` normalises to `undefined`; the app already handles this.
- Menu names are UTF-8 BYTE limited (32), not character limited.
- D6 (Phase 16): `mapEventToGesture` maps every unknown eventType, including
  `undefined`, to TAP. Adding `menuItemClickEvent` must not be swallowed by
  that fallback — check the menu event BEFORE the gesture mapping.

</constraints>
