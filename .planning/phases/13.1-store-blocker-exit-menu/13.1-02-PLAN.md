<objective>
Wire the menu to the app, and delete the state that causes a live soft-brick
while doing it.

Two things that look separate are one thing. `handleMainMenu` case 1 cycles the
battle speed and sets `cursorIndex: 1`. The simulator omits
`currentSelectItemIndex` when the selection is 0 — the same zero-dropping quirk
the app already documents for `CLICK_EVENT` — so `mapEventToGesture` hands
`listIndex: undefined`, `onTap` falls back to `cursorIndex`, which is now
permanently 1, and every subsequent main-menu click re-cycles the speed.
"Enter Battle" becomes permanently unreachable. Verified live (harness-01).

Moving Battle Speed and About into the context menu leaves the list with one
row. `cursorIndex` never leaves 0, so the fallback is harmless. D-05: removing
the state beats guarding it — a special case for index 1 would leave the next
multi-row list free to reintroduce the same bug.

Purpose: INPUT-05, plus a bug that would fail review on its own.
Output: a root menu whose Exit item raises the dialogue, and a main menu that
cannot trap the user.
</objective>

THE CODE BEING REMOVED (ScreenController.ts, `handleMainMenu`) — this is the
soft-brick, quoted exactly so it is recognisable:

```typescript
case 1: // "Battle Speed" — cycle preset inline, re-render with cursor at 1

  this.state = { ...this.state, screen: 'MAIN_MENU', cursorIndex: 1 };   // <- the trap

  break;
```

and the fallback it poisons (`onTap`, unchanged by this plan):

```typescript
const idx = listIndex ?? this.state.cursorIndex;
```

THE MENU IS AN OS AFFORDANCE, NOT AN APP SCREEN. There is no SDK method to open
a menu — the whole bridge surface was checked. The app's only contribution is
declaring `menuObject` on the root page; the firmware (and, in the simulator,
`POST /api/input {"action":"context_menu"}`) opens it and sends back
`menuItemClickEvent`. So "root double-tap opens the menu" is satisfied by
declaring the menu and NOT hijacking the double-tap — there is nothing for the
app to call.

CURRENT DOUBLE-TAP HANDLER: `onDoubleTap()` has no `MAIN_MENU` case and falls
through `default: break`. Task 2 makes that silence explicit rather than
incidental.

RENDER PATH: `render()`'s `MAIN_MENU` case currently calls
`await this.glass.showList(result.items, result.status)`. `END_SCREEN` and
`SPRITE_REFRESH` call `showList` too and must keep passing two arguments — a
rebuild without `menuObject` is what clears the custom menu on non-root pages
(D-09).

4. Add `onMenuItem`, next to `onTap`:
   ```typescript
   /**
    * Native context-menu selection (INPUT-02 / INFO-01).
    *
    * D-03: the root-page guard is the safety mechanism, not a formality. The
    * exit dialogue leaves the firmware unable to send ANY image again until
    * the app restarts (D-02), so the set of places that can raise it is kept
    * to exactly one screen and exactly one explicit selection. Non-root pages
    * rebuild without menuObject and should never deliver these ids at all —
    * this guard is what makes "should" into "cannot".
    *
    * PRECISELY: the guard is STATE-scoped, not page-scoped. `screen` is still
    * 'MAIN_MENU' while the About text page is displayed, so an id arriving
    * there would pass. That is not a hole — the showText rebuild that drew
    * that page carried no menuObject, so the OS has no app menu to deliver
    * from — but the guard reads "the app believes it is on the root screen",
    * not "the root page is on the glass". Say what it does, not more.
    */
   private async onMenuItem(itemID?: number): Promise<void> {
     if (itemID === undefined) return;
     if (this.state.screen !== 'MAIN_MENU') {
       console.log(`[screen] menu itemID=${itemID} ignored on ${this.state.screen}`);
       return;
     }

     switch (itemID) {
       case MENU_ITEM_IDS.exit:
         // INPUT-05: the Even Hub submission requirement. Explicit selection
         // only — never from a double-tap, and never from any other screen.
         console.log('[screen] menu: Exit');
         await this.glass.exitApp();
         break;

       case MENU_ITEM_IDS.battleSpeed:
         console.log('[screen] menu: Battle Speed');
         SpeedConfig.cycle();
         // cursorIndex stays 0. The whole point of D-05 is that no menu action
         // writes a non-zero cursor onto a one-row list.
         await this.render();
         break;

       case MENU_ITEM_IDS.about:
         console.log('[screen] menu: About');
         await this.glass.showText(
           'Pokemon Showdown G2\nGen 9 Random Battles\non Even Realities G2\n\nBuilt with @pkmn/sim\n\nTap to return',
           { left: 'About', right: '' },
         );
         // Screen state stays MAIN_MENU with cursorIndex 0, so the next tap
         // resolves to list item 0 and STARTS A BATTLE — it does not return to
         // the menu. That is pre-existing behaviour (battle.ts:387-388 relies
         // on it to escape the About page) and this phase does not change it.
         // Do not write a comment claiming the tap re-renders the menu.
         // showText rebuilt without menuObject, so the custom menu is cleared
         // while this text page is up — D-09 working as intended.
         break;
     }
   }
   ```
   `console.log`, never `warn`/`error` — the harness fails a run on any console
   error.
