<objective>
Make the menu itself gated: declared at boot, live under `context_menu`,
routed on click, and incapable of bringing harness-01 back.

Two things this plan deliberately does NOT do. It never selects Exit — that is
plan 04's terminal step, placed where a wedged image path can poison nothing.
And it never selects by "whichever item the highlight happens to be on": the
default highlight index is currently an unmeasured assumption, so the harness
navigates by id and treats an Exit selection as a run-fatal bug in its own
navigation.

Purpose: HARN-* already gates this repo. This plan makes INFO-01 and INPUT-02
gated too.
Output: two assertion primitives, a real run-abort, three selfCheck checks and
three boot assertions.
</objective>

WHY A RUN-LEVEL ABORT HAS TO BE ADDED (verified in run.ts):

```typescript
async function runScenario(s, driver, logs, runDir) {
  try { await s.run(ctx); }
  catch (e) { /* records a failed step and RETURNS — the next scenario runs */ }
}
```

So today nothing can stop a run. That is fine for an assertion failure and
wrong for a wedged simulator: the suite shares ONE simulator, and after the
exit dialogue every `updateImageRawData` returns `sendFailed` until restart
(D-02), so every later scenario fails for a reason that has nothing to do with
what it was testing. The outer driver already has the concept — `run.ts:126`
holds `let fatal: string | null` and the main catch at `run.ts:399` sets it and
ends the run. It just has no path from a scenario. This plan adds the path.

REGIONS DOCTRINE (harness/regions.ts header): "Nothing here restates a
coordinate." Every region derives from the app's own layout constants. The OS
context menu is drawn by the firmware/simulator and appears in NO app constant,
so do NOT add a MENU region with hand-measured numbers. Assert on an ink DELTA
over `REGIONS.FULL` plus the byte-difference technique boot.ts step 2 already
uses, and save the frame as the artifact Phase 17 inherits.

THE PROVEN "was the input actually delivered" TECHNIQUE (boot.ts step 2) —
`POST /api/input` answers `{"ok":true}` for inputs the simulator then drops, so
HTTP success proves nothing:

```typescript
if (Buffer.compare(Buffer.from(before.rgba), Buffer.from(after.rgba)) === 0) {
  throw new AssertionError("the framebuffer is byte-identical before and after ...");
}
```

MENU ORDER: `MAIN_MENU_CONTEXT_MENU` is `[Battle Speed, About, Exit]`. Exit is
last so that a menu opened with a default highlight on the first entry cannot
exit. THAT ORDERING IS THE ONLY THING STANDING BETWEEN THIS STEP AND A WEDGED
SIMULATOR, and the "default highlight is index 0" half of it is an assumption
this plan measures rather than trusts.

In `harness/assert.ts`:

1. Add the negative counterpart to `expectLoggedLine`. It has callers in this
   plan and in plan 04, which is why it is a helper rather than an inline find:
   ```typescript
   /**
    * The assertion INPUT-05 actually needs (D-11). The failure this phase
    * exists to prevent is an exit nobody asked for, and the only evidence of
    * it is a line that should not be there — so the check is shaped as an
    * absence. Reports the offending line, because "something exited" with no
    * context is an unactionable failure report.
    *
    * CALLER BEWARE: LogStream.reset() empties the buffer at the start of every
    * ctx.step() that does not pass keepLogs. This assertion only sees the
    * CURRENT step's lines. Asserting "nothing exited during the whole battle"
    * from a step that ran after the battle is vacuous — see plan 04.
    */
   export function expectNoLoggedLine(logs: LogStream, pattern: RegExp, why: string): void {
     const hit = logs.all().find((l) => pattern.test(l.message));
     if (!hit) return;
     throw new AssertionError(`${why}: log line matched ${pattern} — [${hit.source}/${hit.level}] ${hit.message}`);
   }
   ```

2. Add the run-level abort, next to `AssertionError`:
   ```typescript
   /**
    * Stop the ENTIRE run, not just this step.
    *
    * For conditions that invalidate every later scenario rather than failing
    * one: the suite shares one simulator, and once the exit dialogue has been
    * raised every updateImageRawData returns sendFailed until the app restarts
    * (D-02). Continuing past that reports a cascade of failures whose real
    * cause is three scenarios back.
    *
    * Reserved for exactly that. An assertion that is merely FAILED is an
    * AssertionError — downgrading a normal failure to fatal hides every other
    * failure behind the first one.
    */
   export class FatalError extends Error {
     constructor(message: string) {
       super(message);
       this.name = "FatalError";
     }
   }
   ```

In `harness/run.ts`, give `FatalError` the path it needs — inside
`runScenario`'s catch, BEFORE the `record(...)` call:
```typescript
} catch (e) {
  if (e instanceof FatalError) throw e;   // abort the run; the main catch sets `fatal`
  ...existing recording unchanged...
}
```
Import `FatalError` from `./assert.ts` alongside the existing imports. Change
nothing else in run.ts — the main try/catch at the bottom already sets `fatal`
from a thrown error and ends the run, and the teardown already lives in a
`finally`.

In `harness/selfCheck.ts`, APPEND checks after check 52 — never renumber or
weaken an existing one. Extend the existing `../src/config/constants.ts` import
with `MAIN_MENU_CONTEXT_MENU` and `MENU_ITEM_IDS`.

Check 53 — the four protocol rules, enforced LOCALLY so no SDK import is
needed and containerGuards' zero-import doctrine is untouched:
  - every `id` is a non-zero integer;
  - all `id`s are unique;
  - `MAIN_MENU_CONTEXT_MENU.length <= 10`;
  - `Buffer.byteLength(name, "utf8") <= 32` for every name.
  Include a positive control proving the predicate is byte-based, not
  character-based: `"é".repeat(20)` is 20 characters and 40 bytes and MUST be
  rejected by the same predicate. A character check passes it and the firmware
  truncates a name the app can then never address.
  This is the check that stops Phase 17 adding an 11th inspect entry or an
  over-long label and only discovering it when a rejected page builds NOTHING.

Check 54 — Exit is last, and the ids are stable:
  `MAIN_MENU_CONTEXT_MENU.at(-1).id === MENU_ITEM_IDS.exit`, with the reason in
  the failure message: a default highlight lands on the FIRST item, and D-02
  makes an accidental Exit unrecoverable until restart. Also assert
  `MENU_ITEM_IDS.exit === 1` so a future reorder moves the ARRAY POSITION and
  never renumbers an id out from under a saved log line.

Check 55 — `containerTotalNum` counts containers, not menu items. Build the
root page config the app really sends (one list-shaped container with
`isEventCapture: 1`, one status text container with `isEventCapture: 0`,
`containerTotalNum: 2`) plus a `menuObject` carrying three items, and assert
`assertPageContainers(config)` accepts it unchanged. Then assert it REFUSES the
same config with `containerTotalNum: 5` (2 containers + 3 menu items), naming
the mistake: a menu is not a container, and counting menu items into the total
makes the guard refuse every correct root page.
  Use the file's existing local `ContainerLike` / `PageConfigLike` helpers.
  `assertPageContainers` never reads `menuObject` — that is the property being
  pinned here.

Follow the file's existing `check("NN name", () => {...})` shape and its
`refuses...` helper style for the negative arms.
