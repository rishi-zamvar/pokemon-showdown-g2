## THE ANSWER THE PLAN ASKED FOR

**The observed default highlight index is 0 — "Battle Speed", itemID 2.**
**Plan 02 does NOT need revising.** Exit is last and the highlight starts on the
first entry, so the two halves of the safety property are now both measured.

1. Throwaway probe #1 (cold simulator, no harness code involved): `context_menu`
   then a bare `click` produced
   `[EvenAppBridge] EvenHub event: {"jsonData":{"itemID":2},"menuItemClickEvent":{"itemID":2}}`

And visually, from `boot-003-context-menu-open.png`: the panel lists
Battle Speed / About / Exit top to bottom, with **Battle Speed rendered brighter
than the other two** — that is the highlight, on entry one.

## What Shipped

### 1. B3 — the vacuous assertion, fixed where it was vacuous

`harness/scenarios/battle.ts` now calls
`expectNoLoggedLine(ctx.logs, EXIT_CALL, ...)` **inside each `turn-N` step**,
next to that turn's `expectConsoleClean` (battle.ts:463), and once in
`back-to-menu` (battle.ts:611). The original placement in a later coverage step
would have read an empty buffer: `run.ts:177` calls `logs.reset()` at the start
of every step without `keepLogs`, and `logs.reset()` sets `this.lines = []`.

The trap is now documented **on `expectNoLoggedLine`'s own docstring** in
`harness/assert.ts` ("CALLER BEWARE — THIS IS THE ONE ASSERTION THAT CAN PROVE
NOTHING AND SAY NOTHING"), and **selfCheck 56 demonstrates it runnably**: the
same assertion over the same history passes after a `reset()`. A future caller
has to read past a paragraph and a passing-but-vacuous example to repeat it.

### 2. R2 — run-abort containment

- `FatalError` in `harness/assert.ts`.
- One line in `runScenario`'s catch (`run.ts:261`), before the `record(...)`
  that otherwise swallows everything: `if (e instanceof FatalError) throw e;`

## A9 — what the firmware does when `render()` rebuilds a page while the OS menu is open

This happens on **every** menu interaction, twice, and it is benign:

1. **Opening the menu itself triggers a rebuild.** `POST /api/input
   {"action":"context_menu"}` delivers `sysEvent {eventType: 4}` =
   `FOREGROUND_ENTER_EVENT`, which `mapEventToGesture` turns into
   `FOREGROUND_ENTER` and ScreenController answers with a `render()`. The
   simulator logs a full `RebuildPageContainer` — containers, status text and
   `menu_object` — **while the menu is on screen**. The menu stays open and
   stays usable: the very next `click` is delivered as
   `menuItemClickEvent`.
2. **Selecting Battle Speed rebuilds again, under the open menu.** `onMenuItem`
   cycles the preset and awaits `render()`. The rebuild lands (the status
   content in the simulator log changes `Speed: Normal` -> `Speed: Fast`), the
   menu then closes, and a `sysEvent {eventType: 5}` = `FOREGROUND_EXIT_EVENT`
   arrives afterwards.

No `WARN`, no `validation failed`, no dropped input, no visual artefact across
four selections per run and six across the probes. The rebuild is not racing the
menu; the menu is a foreground layer the app's page redraw does not disturb.
Phase 17 can add inspect entries without a menu-lifecycle workaround.

## Navigation shape `selectMenuItem` needed

Minimal: **`context_menu`, then `click`.** No `down` is needed to reach the
default, no `down` is needed before `click` is accepted.

The helper is split in three so the ink measurement can look at an open menu:

- `openMenu(ctx)` — `press("context_menu")` + `quiesce`;
- `commitMenuSelection(ctx, targetIndex)` — `down` x (target - measured
  default), `click`, `refuseExit`, then parse `[GlassAdapter] menu: itemID=(\d+)`
  from lines **at or after a watermark taken before the inputs**;
- `selectMenuItem(ctx, targetIndex)` — the two together.

Three refusals guard it, all of them cheap and all of them about the same
hazard: it refuses a target whose id is `MENU_ITEM_IDS.exit` (plan 04 owns that
selection); it refuses to navigate at all before the default has been measured;
and it refuses a NEGATIVE step count, because only `down` has been measured to
move the OS highlight — `up` has not.

**The `down` path is measured but not exercised by the suite** (probe #2 got
`itemID=3` from one `down`). Every call in this plan targets index 0. Plan 04's
Exit selection is index 2 and will be the first caller to drive it.
