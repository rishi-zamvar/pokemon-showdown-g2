instead of erroring — it renders something plausible and wrong, which is the
worst failure mode there is, because nothing in any log stream says so. The

THE BMP HEADER THE APP ACTUALLY WRITES (src/sprites/SpriteBmpEncoder.ts:61,
`encodeBmp(pixels, width, height)`), BITMAPINFOHEADER, little-endian:

    offset 0   "BM"                      2 bytes, signature
    offset 18  width    setInt32 LE
    offset 22  height   setInt32 LE       positive here = bottom-up rows

A negative height is legal BMP (top-down) — take the absolute value. The app
only ever writes positive, but the reader must not return -132.

PNG, for Phase 15's greyscale pipeline (4 more lines, and REND-04's guard must
not become the thing that blocks it):

    offset 0   \x89PNG\r\n\x1a\n          8 bytes
    offset 16  width    uint32 BE         (IHDR data begins at 16)
    offset 20  height   uint32 BE

Anything else: refuse, naming the first four bytes. Silently accepting an
unrecognised payload defeats the entire point of this guard.

    /**
     * Pixel dimensions of an image payload, read from its own header.
     *
     * Exists because the hardware TILES data smaller than its container rather
     * than erroring: the screen renders something plausible and wrong and no
     * log stream mentions it. Supports the BMP the app writes today and the

    export function imageDataDimensions(data: Uint8Array): { width: number; height: number };

    /** Throws unless `data`'s dimensions equal the container's declared ones. */
    export function assertImageUpdate(
      containerID: number,
      declared: { name: string; width: number; height: number; kind: string } | undefined,

    exactly where this kind of reader silently reads the wrong bytes.
