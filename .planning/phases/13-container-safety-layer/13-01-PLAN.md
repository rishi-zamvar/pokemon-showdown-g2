  <files>src/adapters/containerGuards.ts, harness/selfCheck.ts</files>
  <behavior>
    Checks to add to harness/selfCheck.ts, numbered from 39, before writing the
    implementation. Each uses a manually-settled promise, never a timer — a
    sleep-based test of a concurrency bug is a coin flip.

    - 39 "SendQueue.run does not start task N+1 until task N settles":
      submit three tasks that each record `started` and return a deferred
      promise. Assert only task 1 started. Resolve task 1 -> assert task 2
      started and task 3 has not. Resolve task 2 -> task 3 started.
      MICROTASK TIMING, or this check fails against a CORRECT queue and the
      executor "fixes" the queue instead of the check: `run()` is not async
      and `tail` starts as `Promise.resolve()`, so even task 1 begins one
      microtask turn after submission, not synchronously. Put
      `await Promise.resolve()` before EVERY assertion block, including the
      first one.
    - 39b (same check): results resolve in submission order with the right
      values, and each caller gets its OWN task's value, not its neighbour's.
    - 40 "a rejected send does not poison the queue": task 1 rejects; assert
      the rejection reaches task 1's caller AND that task 2 still runs and
      resolves. (A plain `tail = tail.then(fn)` fails this — that is the point
      of the check.)
    - 41 "the concurrency detector used by check 39 can still detect
      concurrency": run the SAME three tasks WITHOUT the queue (bare
      Promise.all) and assert all three report started before any settles.
      Without this, checks 39/40 would also pass against a queue that never
      runs anything, and the falsifiability obligation is unmet.
  </behavior>
  <action>
    Create `src/adapters/containerGuards.ts` — the container safety layer.
    Plans 13-02 and 13-03 add the geometry and dimension guards to this same
    file; it holds only the queue today.

    Export one class:

    ```typescript
    /**
     * The platform rule this exists for: "Concurrent sends: Not allowed -
     * queue image updates sequentially." AnimationEngine.ts:282 runs
     * spriteFlash and hpDrain as concurrent Promise.all branches and both
     * issue updateImageRawData; the bridge deadlocks roughly one turn in
     * twenty (research-14). Serialising HERE fixes every caller, including the
     * ones that do not exist yet.
     */
    export class SendQueue {
      // NOT a constructor parameter property: Node strips types only and
      // rejects those at runtime while tsc stays silent (see harness/logs.ts:121).
      private tail: Promise<unknown> = Promise.resolve();

      run<T>(fn: () => Promise<T>): Promise<T> {
        // .then(fn, fn): a prior send that REJECTED must not block the sends
        // queued behind it — one failed frame would otherwise wedge the game
        // exactly as badly as the deadlock this replaces.
        const result = this.tail.then(fn, fn);
        // swallow separately so the queue's own copy never becomes an
        // unhandled rejection, while the caller's copy still rejects.
        this.tail = result.then(() => undefined, () => undefined);
        return result;
      }
    }
    ```

    Everything the app sends is queued, not just image data: a
    `rebuildPageContainer` racing an `updateImageRawData` is the same class of
    bug, and one queue is less code than two.

    It does NOT supersede the 50 ms sleep at glassAdapter.ts:449. The queue
    prevents two sends OVERLAPPING; it does not make a caller's rebuild-then-
    send sequence atomic, because the delays and the intervening app code sit
    outside the queue and another caller's send can still slip between them.
    That sleep stays, and stays deferred.

    THE COST IS SECONDS PER TURN, NOT MILLISECONDS. Be honest about it up
    front so task 3 does not read the true number as a failure. During a
    DAMAGE entry three branches offer load at once: the typewriter issues one
    text update per ~149 ms, spriteFlash one image per ~179 ms, hpDrain one
    per ~144 ms. At ~104 ms of service time each that is
    104 x (1/149 + 1/179 + 1/144) ~= 1.98 — roughly 2x saturated on a
    single-server queue. Wall time per entry therefore moves from
    max(branches) to about sum(sends): a 40-character DAMAGE entry goes from
    ~6 s to ~7.5 s, and a turn with several entries gains single-digit
    seconds. Against a 120 s TURN_MS budget and turns measured at 8-40 s that
    is comfortable, and it buys a game that does not stop forever. Task 3
    records the real figure.

    Then add checks 39, 40 and 41 to `harness/selfCheck.ts`, importing from
    `"../src/adapters/containerGuards.ts"` (explicit extension — Node needs it).
  </action>
