<objective>
Make it impossible for the adapter to declare a page the firmware will reject.
One oversized container fails the ENTIRE `rebuildPageContainer` — that is what
made the game unplayable in defect #2, not a partial render — so the guard runs
before the call and refuses loudly (D-02). It never clamps: a container outside
the limits is a layout bug in the caller, and quietly resizing it would render
the wrong page instead of failing.

Two guards, not one, because neither is sufficient (D-05). I verified the SDK's
`validateEvenHubPageContainer()` live: it returned `{valid: true}` for a
9999x9999 image container and for `containerTotalNum: 13`. It covers z-order,
menus and text brightness — nothing this phase is about. Ours covers geometry
and counts — nothing the SDK's is about.

Purpose: every later phase adds containers; this is the tripwire that makes a
bad one fail at the adapter with a named reason instead of silently blanking
the screen.
Output: `assertPageContainers()`, the SDK validator wired in, and the cumulative
container registry that plan 13-03 needs.
</objective>

WHY THE REGISTRY IS CUMULATIVE, NOT PER-PAGE. glassAdapter.ts:283 documents the
measured behaviour: `rebuildPageContainer` does NOT remove containers absent
from the new config — they persist on screen with their last content. That is
why both blanking workarounds exist. So "does this container exist on the
hardware" means "was it ever declared by a SUCCESSFUL create/rebuild", not
"is it in the current config". Model it that way or plan 13-03's fix for
research-10/11 will be wrong in the opposite direction.

  <name>Task 2: Wire both validators in, and start the container registry</name>
  <files>src/adapters/glassAdapter.ts</files>
  <action>
    In `renderContainers()` and `bootstrapStartup()`, immediately after `config`
    is built and BEFORE any bridge call:

    ```typescript
    this.assertPage(config);
    ```

    ```typescript
    /**
     * Two guards, because neither covers the other (D-05). The SDK's validator
     * returned {valid:true} for a 9999x9999 image container and for
     * containerTotalNum:13 — verified live — so it cannot be trusted for
     * geometry or counts; ours does not cover z-order, menus or text
     * brightness, so it cannot replace the SDK's either.
     */
    private assertPage(config: PageConfigLike & EvenHubPageContainerLike): void {
      assertPageContainers(config);                       // throws, message already prefixed
      const r = validateEvenHubPageContainer(config);
      if (!r.valid) {
        const detail = formatEvenHubPageContainerValidationError(r);
        console.error(`[glass] adapter: rejected container page (SDK): ${detail}`);
        throw new Error(`adapter: rejected container page (SDK): ${detail}`);
      }
    }
    ```

    `assertPageContainers` should `console.error` its own line before throwing,
    so the refusal is visible in the harness console stream even when a caller
    swallows the exception. Both paths therefore emit `adapter: rejected
    container`. Put the console.error in the adapter (one place, wrapping the
    throw) rather than inside the pure guard, so the guard stays side-effect
    free and testable — catch, log, rethrow.

    Then add the registry:

    ```typescript
    /**
     * Every container ever successfully declared, with its latest dimensions.
     *
     * CUMULATIVE on purpose: rebuildPageContainer does NOT remove containers
     * absent from the new config (see the comment at showBattleHud), so a
     * container declared by an earlier page is still addressable. A per-page
     * map would make plan 13-03 refuse updates that are perfectly legal.
     */
    private readonly declaredContainers = new Map<number, {
      kind: "image" | "text" | "list"; name: string; width: number; height: number;
    }>();
    ```

    are THREE population points and one deliberate non-point; enumerate them,
