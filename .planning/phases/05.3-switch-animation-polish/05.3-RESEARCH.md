# Phase 5.3: Switch Animation & Text Polish - Research

**Researched:** 2026-02-27
**Domain:** Pokemon Showdown protocol parsing, BMP sprite generation, animation sequencing
**Confidence:** HIGH

---

## Summary

This research covers three parallel concerns for Phase 5.3:

1. **Complete PS protocol text coverage** — The @pkmn/sim text data is embedded directly in the package at `build/esm/data/text/default.mjs` and `build/esm/data/text/moves.mjs`. All exact PS text strings have been verified from the live `play.pokemonshowdown.com/data/text/misc.json5` endpoint AND from the installed package source. These two sources agree exactly (the package ships the same strings). Every message type needed for this phase has been documented with exact strings below.

2. **BMP sprite generation** — The existing `SpriteBmpEncoder.ts` exposes `encodeBmp(pixels, width, height)` as the internal function and `emptyBmp(size)` as a public helper. Programmatic generation of pokeball/square/checkbox frames requires calling `encodeBmp` with a hand-crafted `pixels` Uint8Array. The pixel format is row-major, top-to-bottom (the encoder internally inverts to BMP bottom-up). Sprite size is 96x96 (SPRITE_CONFIG.SIZE).

3. **Volatile status access** — The sim's `Pokemon.volatiles` is `{ [id: string]: EffectState }`. A volatile is present as a key when active, absent when not. Key names are lowercase slugs: `'confusion'`, `'leechseed'`, `'substitute'`, `'taunt'`, `'encore'`, `'disable'`, `'curse'`, `'mustrecharge'`, `'focusenergy'`, `'trapped'`, etc.

**Primary recommendation:** Parse every PS protocol line in LogParser.ts by adding cases for all documented message types. Map each to a new TurnLogEntry kind or collapse rare/silent ones into a generic TEXT kind. Generate BMP frames using the existing `encodeBmp` internal function extracted to a new `AnimationFrames.ts` module.

### Pattern 4: Programmatic BMP Frame Generation

The `encodeBmp` function is currently unexported (private). It must be exported from `SpriteBmpEncoder.ts`.

```typescript
// In SpriteBmpEncoder.ts — export the internal encoder:
export function encodeBmp(pixels: Uint8Array, width: number, height: number): Uint8Array { ... }

// In AnimationFrames.ts — NEW module:
import { encodeBmp } from '../sprites/SpriteBmpEncoder.js';
import { SPRITE_CONFIG } from '../config/constants.js';

const SIZE = SPRITE_CONFIG.SIZE; // 96

/** Draw a circle (pokeball approximation) centered in SIZE×SIZE frame. */
export function makePokeballFrame(): Uint8Array {
  const pixels = new Uint8Array(SIZE * SIZE);
  const cx = SIZE / 2;
  const cy = SIZE / 2;
  const r = SIZE * 0.35; // ~33px radius
  for (let y = 0; y < SIZE; y++) {
    for (let x = 0; x < SIZE; x++) {
      const dx = x - cx;
      const dy = y - cy;
      const dist = Math.sqrt(dx * dx + dy * dy);
      // Outline circle: 1px ring
      if (dist >= r - 1 && dist <= r + 1) {
        pixels[y * SIZE + x] = 1;
      }
    }
  }
  return encodeBmp(pixels, SIZE, SIZE);
}

/** All-white filled square (green filled square → white on 1-bit display). */
export function makeFilledSquareFrame(): Uint8Array {
  const pixels = new Uint8Array(SIZE * SIZE).fill(1); // all white
  return encodeBmp(pixels, SIZE, SIZE);
}

/** White square with black inner region (checkbox approximation). */
export function makeCheckboxFrame(): Uint8Array {
  const pixels = new Uint8Array(SIZE * SIZE);
  const border = Math.round(SIZE * 0.1); // ~10px border
  const checkSize = Math.round(SIZE * 0.3); // ~29px checkmark area
  const cx = SIZE / 2;
  const cy = SIZE / 2;
  for (let y = 0; y < SIZE; y++) {
    for (let x = 0; x < SIZE; x++) {
      // Outer border: white
      if (x < border || x >= SIZE - border || y < border || y >= SIZE - border) {
        pixels[y * SIZE + x] = 1;
      }
      // Center checkmark area: white pixels in a tick shape
      const dx = Math.abs(x - cx);
      const dy = Math.abs(y - cy);
      if (dx + dy < checkSize * 0.7) {
        pixels[y * SIZE + x] = 1;
      }
    }
  }
  return encodeBmp(pixels, SIZE, SIZE);
}
```

**IMPORTANT:** The `pixels` array is row-major, top-to-bottom (y=0 is the TOP row). The `encodeBmp` function internally converts to BMP bottom-up format. Do NOT pre-invert the rows.

### Pattern 5: Switch Animation Sequence

The `resolveSwitch()` in `ScreenController.ts` currently skips all animation. It must be updated to call `animationEngine.playTurn()` like `resolveTurn()` does.

The SWITCH TurnLogEntry should trigger a 3-frame animation in `AnimationEngine.playEntry()`:

```typescript
// In AnimationEngine.playEntry() — new SWITCH case:
if (entry.kind === 'SWITCH') {
  const switchedSide: Side = entry.actor;  // which side switched
  const containerID = switchedSide === 'opponent'
    ? CONTAINER_IDS.oppSprite
    : CONTAINER_IDS.playerSprite;
  const containerName = switchedSide === 'opponent'
    ? CONTAINER_NAMES.oppSprite
    : CONTAINER_NAMES.playerSprite;

  // Frame 1: pokeball
  await glass.updateImage(containerID, containerName, AnimationFrames.makePokeballFrame());
  // Frame 2: filled square
  await glass.updateImage(containerID, containerName, AnimationFrames.makeFilledSquareFrame());
  // Frame 3: checkbox square
  await glass.updateImage(containerID, containerName, AnimationFrames.makeCheckboxFrame());
  // Frame 4: real pokemon sprite (from nextState)
  const newSprite = getSpriteForSide(nextState, switchedSide);
  if (newSprite) {
    await glass.updateImage(containerID, containerName, newSprite);
  }
}
```

**No artificial delays** between frames — each `await glass.updateImage()` provides natural pacing.

### Pattern 6: HUD Volatile Status Display

The `ActivePokemon` type needs a new `volatiles` field:

```typescript
export interface ActivePokemon extends BattlePokemon {
  currentHp: number;
  status: StatusCondition;
  toxicCounter: number;
  sleepTurns: number;
  teraActive: boolean;
  ppUsed: Record<string, number>;
  fainted: boolean;
  volatiles: string[];  // NEW: list of active volatile abbreviations e.g. ['CNF', 'TAUNT']
}
```

HUD format with new decision (single bracket):
```typescript
// In battleHudRenderer.ts formatName():
function formatName(label: string, mon: ActivePokemon): string {
  const parts: string[] = [];
  if (mon.teraActive) parts.push(mon.teraType);
  if (mon.status) parts.push(mon.status.toUpperCase());
  parts.push(...mon.volatiles); // CNF, TAUNT, etc.

  if (parts.length === 0) return `${label}: ${mon.name}`;

  // Truncate to fit 64-char line limit
  let partsStr = parts.join(', ');
  const base = `${label}: ${mon.name} (`;
  if (base.length + partsStr.length + 1 > 64) {
    // Truncate with ellipsis
    while (base.length + partsStr.length + 4 > 64 && parts.length > 0) {
      parts.pop();
      partsStr = parts.join(', ') + '...';
    }
  }
  return `${base}${partsStr})`;
}
```

### Anti-Patterns to Avoid

- **Using `line.includes()` instead of `parts[1]`:** Always split on `|` and check `parts[1]` for the command. `line.includes('-boost')` would also match comments and other data.
- **Reading HP from log strings for state:** Already avoided — HP is read from sim fields. Log HP strings are only for animation `targetHp`/`targetMaxHp`.
- **Blocking animation with await delay():** Switch animation has no artificial delays — just `await glass.updateImage()` for each frame. Hardware round-trip IS the frame timing.
- **Holding sim Pokemon references across turns:** Already documented in SimBattleAdapter. Do not store sim Pokemon objects — read all needed data immediately and release.
- **Checking `parts[4]` without checking `parts[3]` first:** The `[from]` tag may not always be at a fixed index. Use `parts.findIndex(p => p.startsWith('[from]'))` for robustness.
- **Generating BMP frames at runtime per-frame:** Cache the three animation frames (pokeball, filled square, checkbox) at module load time — they are constant.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| BMP encoding | Custom binary writer | `encodeBmp()` in SpriteBmpEncoder.ts | Already handles header, stride, bottom-up format |
| Protocol parsing | Regex on raw lines | `line.split('|')` parts array | PS protocol is strictly `|`-delimited |
| Text lookup | Hardcode strings | Exact strings from PS source (documented below) | Must match PS exactly |
| Volatile check | Complex condition evaluation | `!!simMon.volatiles['name']` | Direct object property check is authoritative |

## BMP Format Details (HIGH confidence — verified from SpriteBmpEncoder.ts source)

The Even G2 SDK expects 1-bit monochrome BMP. The existing encoder produces:

```
File structure:
- BMP file header: 14 bytes (signature 'BM', fileSize, reserved, pixelDataOffset=62)
- BITMAPINFOHEADER: 40 bytes (width, height positive=bottom-up, planes=1, bpp=1, compression=0)
- Color table: 8 bytes (2 colors × 4 bytes: black=0x00000000, white=0x00FFFFFF)
- Pixel data: rowStride × height bytes
  - rowStride = ceil(ceil(width/8) / 4) × 4  (4-byte row alignment)
  - For 96×96: rowStride = 16 bytes, pixelData = 1536 bytes
  - Total file: 62 + 1536 = 1598 bytes

Pixel encoding:
- Bit 7 of first byte = leftmost pixel (x=0)
- 1 bit = white, 0 bit = black
- Rows stored bottom-up (y=0 of BMP = bottom of image)
- encodeBmp() handles the inversion: pass pixels[y*w+x] top-down, function inverts
```

**Programmatic frame pixel conventions:**
- White pixels (value=1) appear bright on the glasses display
- Black pixels (value=0) are the background/off

The three animation frames should all be 96×96 pixels (SPRITE_CONFIG.SIZE = 96).

## Common Pitfalls

### Pitfall 1: Missing the `[upkeep]` tag for weather
**What goes wrong:** |-weather|RainDance shows "It started to rain!" when it's actually just ticking.
**Why it happens:** Weather has three states: start, upkeep (continuing), end. The `[upkeep]` keyword appears in parts[3+] of the line.
**How to avoid:** Check `parts.includes('[upkeep]')` before showing start text. Upkeep messages should be suppressed or shown as brief status text only.
**Warning signs:** Weather text shows every turn instead of just when it starts/ends.

### Pitfall 2: activeIndex not updating after forced switch
**What goes wrong:** After a faint-switch, the HUD still shows the fainted Pokemon's sprite and stats.
**Why it happens:** `resolveSwitch()` in ScreenController.ts currently calls `render()` without running `playTurn()` animation first. The `deriveSide()` function does compute the correct activeIndex from sim state, but the animation must also show the new sprite.
**How to avoid:** Modify `resolveSwitch()` to call `animationEngine.playTurn(log, prevState, nextState, glass)` before `render()`, same as `resolveTurn()` does.
**Warning signs:** Blank sprite or wrong Pokemon name after forced switch.

### Pitfall 3: Duplicate events from split-protocol
**What goes wrong:** Events like |-damage| appear twice in the log.
**Why it happens:** The sim uses `addSplit()` which creates: |split|p1 → secret line → shared line. The `filterSplitLines()` function in SimBattleAdapter handles this but must run BEFORE parseLogLines.
**How to avoid:** Already handled. Verify that `filterSplitLines` runs on the buffer before parsing. Do not bypass it.
**Warning signs:** Double damage text, double boost text in a single turn.

### Pitfall 4: |-start| vs |-activate| vs |-singleturn| confusion
**What goes wrong:** Confusion damage shows wrong text, or protect text fires from the wrong message.
**Why it happens:**
- `|-start|POKEMON|confusion` = confusion inflicted (show "became confused!")
- `|-activate|POKEMON|confusion` = pokemon hit itself due to confusion (show "is confused!")
- |-damage| with `[from] confusion` = the actual confusion self-hit damage (show "It hurt itself in its confusion!")
- `|-singleturn|POKEMON|move: Protect` = protect used (show "protected itself!")
**How to avoid:** Parse `|-start|`, `|-activate|`, `|-singleturn|` as distinct cases. The effect name in parts[3] determines the text.
**Warning signs:** "became confused!" showing every confused turn instead of just on infliction.

### Pitfall 5: Weather ID vs effect name mismatch
**What goes wrong:** `|-weather|SunnyDay` not matching "sun" text lookup.
**Why it happens:** The protocol uses the move name (`SunnyDay`, `RainDance`, `Sandstorm`, `Hail`, `Snowscape`) not the weather name.
**How to avoid:** Build a lookup map: `{ 'SunnyDay': sunnyday, 'RainDance': raindance, 'Sandstorm': sandstorm, 'Hail': hail, 'Snowscape': snowscape }`.
**Warning signs:** Generic fallback text for weather instead of specific text.

### Pitfall 6: Side effect [TEAM] substitution
**What goes wrong:** "Pointed stones float in the air around [TEAM]!" renders literally with `[TEAM]`.
**Why it happens:** The PS text uses `[TEAM]` as a placeholder. The side `p1`/`p2` in parts[2] must be mapped to "your team" or "the opposing team".
**How to avoid:** In formatEntry for SIDE_START/SIDE_END, substitute `[TEAM]` based on actor.
**Warning signs:** "[TEAM]" appears verbatim in the glasses display.

### Pitfall 7: Heal animation direction
**What goes wrong:** HP bar animates down instead of up for healing.
**Why it happens:** hpDrain() in AnimationEngine always subtracts HP. Healing needs the reverse.
**How to avoid:** Add an `hpHeal()` method that interpolates from `startHp` to `endHp` where `endHp > startHp`. Use the same step-based animation but incrementing.
**Warning signs:** HP bar briefly drains then jumps to healed value.

### Pitfall 8: BMP pixel array orientation
**What goes wrong:** Programmatic sprites appear flipped vertically.
**Why it happens:** Confusion between top-down pixel array and BMP bottom-up storage. The `encodeBmp()` function handles this — pass pixels top-down and it stores bottom-up.
**How to avoid:** Draw pixels with `y=0` as the TOP row of the sprite. `encodeBmp()` handles inversion internally.
**Warning signs:** Pokeball appears upside down.

## Open Questions

1. **`|-activate|` handling — case-by-case**
   - What we know: `|-activate|POKEMON|EFFECT` covers Substitute damage, Baton Pass, ability triggers, etc.
   - What's unclear: Many `|-activate|` messages have different text depending on the effect. Full coverage requires a large lookup table.
   - Recommendation: Handle common ones (substitute damage: "The substitute took damage for [POKEMON]!", confusion: "is confused!", struggle: "[POKEMON] has no moves left!") — use generic fallback for unknown activates.

2. **`|-enditem|` with Eject Button / Red Card**
   - What we know: These items cause switches. The item is consumed and then a switch happens.
   - What's unclear: Whether a special text is needed or if the subsequent |drag| covers it.
   - Recommendation: Show "[POKEMON]'s [ITEM] was used!" for enditem — the drag/switch protocol handles the switch.

3. **`|-start|` for two-turn moves (twoturnmove volatile)**
   - What we know: Moves like Fly, Dig set a `twoturnmove` volatile on turn 1.
   - What's unclear: Whether this emits a |-start| that needs text, or if |-prepare| covers it.
   - Recommendation: Use |-prepare| text for two-turn charge display; ignore `twoturnmove` volatile start if it has no text entry.

4. **Pixel layout for pokeball frame**
   - What we know: Must be recognizable as "switch incoming" on a 96×96 1-bit display.
   - What's unclear: Whether a circle outline is visible enough on the tiny glasses display.
   - Recommendation: Use a filled circle with hollow center (ring) for pokeball, then full white square, then white square with X cross for checkbox. Iterate based on testing.
