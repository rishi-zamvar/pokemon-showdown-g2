Build the ScreenController class -- the screen state machine that routes gestures to screen transitions and battle engine calls.

Purpose: This is the brain of the UI layer. It holds screen state (which screen, cursor, battleState), maps gestures to actions, calls renderers to get content, and pushes content to the glass display. All battle logic flows through it: tap on attack -> AI picks action -> engine resolves turn -> show result -> advance to next screen.

Output: A single ScreenController.ts that implements the complete navigation graph and turn resolution flow.

  <action>
Create `src/screens/ScreenController.ts` as a class that:

**Constructor:**
- Takes `GlassAdapter` (from contracts.ts interface) as dependency
- Initializes `ScreenState` with `{ screen: 'MAIN_MENU', cursorIndex: 0, battleState: null }`
- Stores a `lastTurnLog: TurnLogEntry[]` for turn result display
- Stores a `switchIndexMap: number[]` for mapping switch display indices to team indices
- Stores a `forcedSwitch: boolean` flag for forced vs voluntary switch

**Public methods:**

`async init(): Promise<void>` -- Renders the main menu on glasses. Called once after construction.

`async handleGesture(event: GestureEvent): Promise<void>` -- Main entry point. Routes based on `event.kind`:
  - `TAP`: Calls `onTap(event.listIndex)`
  - `SCROLL_FWD` / `SCROLL_BACK`: Only relevant on text screens where we might want to page -- but per research, these are BOUNDARY events and lists handle scroll internally. For text screens (BATTLE_HUD, TURN_RESULT), ignore scroll entirely. For list screens, the firmware handles cursor movement via `isItemSelectBorderEn: 1`, so also ignore scroll in the controller. Do nothing for scroll events.
  - `FOREGROUND_ENTER`: Re-render current screen
  - `FOREGROUND_EXIT`: No-op

**Private: `onTap(listIndex?: number)`** -- The core routing logic. Switch on `this.state.screen`:

**MAIN_MENU:**
- Any tap (index 0 = "Enter Battle"): Call `startNewBattle()`

**BATTLE_HUD:**
- Any tap: Navigate to ACTION_MENU, render action menu

**ACTION_MENU:**
- Index 0 ("< Back"): Go back to BATTLE_HUD
- Index 1 ("Attack"): Go to ATTACK_SELECT
- Index 2 ("Switch"): Go to SWITCH_SELECT (voluntary, `forcedSwitch = false`)
- Index 3 ("Terastallize"): If `playerSide.teraUsed`, ignore tap (already used). Otherwise go to TERA_CONFIRM.

**ATTACK_SELECT:**
- Index 0 ("< Back"): Go back to ACTION_MENU
- Index 1-4 (moves): Get the move slug from `state.battleState.playerSide.team[activeIndex].moves[index - 1]`. Call `resolveTurn({ type: 'ATTACK', moveSlug })`.

**SWITCH_SELECT:**
- Index 0 ("< Back"): If `forcedSwitch`, ignore (cannot go back on forced switch). Otherwise go back to ACTION_MENU.
- Index 1+: Map display index to team index via `switchIndexMap[index - 1]`. If voluntary switch, call `resolveTurn({ type: 'SWITCH', toIndex })`. If forced switch, call `resolveSwitch(toIndex)`.

**TERA_CONFIRM:**
- Index 0 ("< Back"): Go back to ACTION_MENU
- Index 1 ("Confirm"): Get the best move slug (first move with PP remaining) and call `resolveTurn({ type: 'TERA_ATTACK', moveSlug })`. For move selection: reuse the same logic as attackSelect -- show the attack select screen after tera confirm, OR simpler: just pick the first move with PP. Research shows the common pattern is Tera + attack in one action. The BattleEngine supports `TERA_ATTACK` which activates Tera and attacks in one action. So on confirm, navigate to ATTACK_SELECT but set a flag `teraQueued = true`. When a move is then selected from ATTACK_SELECT, use `TERA_ATTACK` instead of `ATTACK`.

Actually, cleaner approach based on the engine API: After confirming Tera, go to ATTACK_SELECT. Store `teraQueued = true`. When the player picks a move from ATTACK_SELECT while `teraQueued`, send `{ type: 'TERA_ATTACK', moveSlug }` instead of `{ type: 'ATTACK', moveSlug }`. Reset `teraQueued` after use.

**TURN_RESULT:**
- Any tap: Advance to the next screen based on `state.battleState.phase`:
  - `WAITING_FOR_ACTION` -> BATTLE_HUD
  - `WAITING_FOR_SWITCH` -> SWITCH_SELECT (forced, `forcedSwitch = true`)
  - `BATTLE_OVER` -> END_SCREEN

**END_SCREEN:**
- Index 0 ("New Battle"): Call `startNewBattle()`
- Index 1 ("Main Menu"): Go to MAIN_MENU, clear battleState

**Private: `startNewBattle()`:**
1. Show loading message: `glass.showMessage('Generating teams...')`
2. `const state = BattleEngine.startBattle()`
3. Store `state` in `this.state.battleState`
4. Set screen to `BATTLE_HUD`, render

**Private: `resolveTurn(playerAction: PlayerAction)`:**
1. Get AI action: `const aiAction = AIOpponent.pickAction(state.battleState!)`
2. Submit to engine: `const result = BattleEngine.submitAction(state.battleState!, playerAction, aiAction)`
3. Store `result.log` in `lastTurnLog`
4. Update `state.battleState = result.nextState`
5. Set screen to `TURN_RESULT`, render

**Private: `resolveSwitch(toIndex: number)`:**
This handles FORCED switch after a faint.
1. First, check if the OPPONENT's active is also fainted (double faint scenario from research open question #2). If so, auto-pick opponent's first alive non-active Pokemon and call `BattleEngine.submitSwitch(state, 'opponent', aiSwitchIndex)` first. Update state.
2. Then call `BattleEngine.submitSwitch(state, 'player', toIndex)`.
3. Store result log, update battleState.
4. Check `result.nextState.phase`:
   - `WAITING_FOR_ACTION` -> BATTLE_HUD
   - `WAITING_FOR_SWITCH` -> Stay on SWITCH_SELECT (other side still needs switch -- shouldn't happen after we handled opponent above, but defensive)
   - `BATTLE_OVER` -> END_SCREEN
5. Render appropriate screen.

**Private: `render()`:**
Switch on `this.state.screen` to call the appropriate renderer and glass method:
- `MAIN_MENU`: `renderMainMenu()` -> `glass.showList(result.items, result.status)`
- `BATTLE_HUD`: `renderBattleHud(state.battleState!)` -> `glass.showText(result.text, result.status)`
- `ACTION_MENU`: `renderActionMenu({ teraUsed })` -> `glass.showList(...)`
- `ATTACK_SELECT`: `renderAttackSelect(state.battleState!)` -> `glass.showList(...)`
- `SWITCH_SELECT`: `renderSwitchSelect(state.battleState!, forcedSwitch)` -> store `indexMap`, `glass.showList(...)`
- `TERA_CONFIRM`: `renderTeraConfirm(state.battleState!)` -> `glass.showList(...)`
- `TURN_RESULT`: `renderTurnResult(lastTurnLog)` -> `glass.showText(...)`
- `END_SCREEN`: `renderEndScreen(state.battleState!.winner!)` -> `glass.showList(...)`

For all tap handlers, always use `const idx = listIndex ?? this.state.cursorIndex` to handle undefined listIndex (Pitfall 5 from research). On text screens (BATTLE_HUD, TURN_RESULT), ignore listIndex entirely -- any tap triggers the action.

**Important implementation details:**
- Use `.js` extensions in all imports (ESM)
- Import types from `../types/battleState.js` and `../types/contracts.js`
- Import all renderer functions from `./renderers/*.js`
- Import BattleEngine from `../battle/BattleEngine.js`
- Import AIOpponent from `../battle/AIOpponent.js`
- The `teraQueued` flag must be reset in ALL paths that leave ATTACK_SELECT (back, move selection), not just on successful tera use
- DataLoader.loadMatchData() must be called after startBattle() with the 12 Pokemon -- check if BattleEngine.startBattle() already handles this. Looking at the code, it does NOT call loadMatchData. So in `startNewBattle()`, after getting the state, call `await DataLoader.loadMatchData(allSpeciesSlugs)` where allSpeciesSlugs combines both teams' species names lowercased. Then render.
- Actually, check if DataLoader.loadMatchData exists and what it needs. It was created in Phase 1 (01-03). It takes species slugs for the 12 Pokemon and loads their learnset data. Call it with the 12 species from both teams.
